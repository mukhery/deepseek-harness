# Agent Note: Crew progress-monitoring panel (ticket board + escalation surfacing)

Status: implemented

## Problem

[Director-led crew](../../implemented/feature/2026-08-20-director-led-crew.md) gave `ctx.crew` a durable workspace-scoped roster and ticket ledger, but shipped no way to see it: no host-plane RPC exposed `ctx.crew.roster()`/`.tickets()`, no session event carried it, and the web client referenced `crew` nowhere outside its own test fixture. A user running a Director thread over days had no way to see the ticket board, which tickets were blocked, or why, short of reading raw `crew_board` tool-call JSON in the transcript. This change adds a read-only "Crew" tab to the existing sidebar workspace browser: a kanban-style ticket board plus an escalation banner for blocked tickets. Scope, confirmed before implementation: ticket board + roster (for assignee labels) + escalation linkage only — the structured message pool (`messages` table, `crew_publish`/`crew_read_pool`) stays out of scope for this pass, same as the roster/ticket-only scope the sidebar's existing session rows already model.

## Decision

**Wire mechanism: ApiProxy, not Typert Remote.** `packages/api`'s `@Remote` system is one-shot request/response only — its own design note states live/stateful streams "remain separate designs." Crew's requirement is live, event-driven updates (a ticket board that stays current while a Director works), so this uses the same mechanism `workspace.*` already uses: a unary baseline RPC (`crew.board`) plus a push `HostFrame` (`host/crew-board-changed`), both driven off `ctx.on('domain/changed', ...)` at commit time, mirroring `packages/host/apiproxy/src/api-proxy.ts`'s existing `workspace` domain/changed listener almost exactly — a second, parallel listener was added rather than restructuring the existing one, since the two domains have different scoping shapes (workspace's own two-level global/table split vs. crew's every-record-carries-`workspaceId` shape, which needs no committed-set baseline at all).

**No new package; `ctx.crew` read as an optional service.** Wire types/schemas/RPC/frame went into the existing `packages/host/apiproxy` (the established seam for every read-domain), following `workspace.ts`/`workspace.schema.ts` file-for-file, including re-declaring `CrewRole`/`CrewTicketStatus`/`CrewTicketId` locally rather than importing `@deepseek-ai/dsh-crew`'s own types, for the same reason `workspace.ts` documents: `api/` must stay browser-importable with zero host-package dependencies. `CrewRosterView`/`CrewTicketView` are the identity projection of `CrewRosterRecord`/`CrewTicketRecord` — every field was already client-safe. `apiproxy` depends on `@deepseek-ai/dsh-crew` only for its runtime type merge and the two durable-record zod schemas used to parse `domain/changed`'s `value`; `ctx.get('crew')` is read as an optional service (`?? []` on both `roster()`/`tickets()`), so a composition without the crew package mounted still answers `{ roster: [], tickets: [] }` from `crew.board` rather than failing — `ctx.crew` is already mounted host-globally in `packages/bundle/web-app/cordis.patch.yml`, but apiproxy itself must not hard-require it, matching the existing `jobs`/`sessionProjections` optional-service posture in the same file.

**Read-only; no mutation RPC.** All crew writes stay tool-mediated (`crew_hire`/`crew_assign_ticket`/`crew_verdict`/etc., unchanged); the panel only reads. This mirrors crew's own design (see the linked note's "enforce a decision in the operation that makes it" rule) — a mutation RPC here would be a second, weaker-checked write path onto state whose authority already lives in `CrewRuntime`'s role/assignee checks.

**Escalation linkage is inferred client-side, not backend-linked.** There is no ticket↔question link field, and none was added: a ticket's `blockedReason` is already the human-facing text, and `pendingInteraction === 'question'` on a session is already computed entirely client-side from mux frames. The Director is never on the crew roster (only hired children are), so correlation is: within the current workspace, find sessions where `agentPreset === 'crew-director'` AND `pendingInteraction === 'question'`, cross-referenced against tickets where `status === 'blocked'` (`packages/client/ui-workspace/src/client/crew/crew-tree.ts`'s `deriveEscalationBanner`). This is a heuristic, documented as one in the derivation's own JSDoc and the ui-workspace README's Known Limitations, not a guarantee: a Director could be asking an unrelated question, and multiple candidate sessions resolve to whichever is found first. The banner shows whenever ≥1 ticket is blocked regardless of a match — the human may need to open a *new* Director thread — with a direct "go to session" CTA only when a match exists.

**No SDK dual-projection update.** This is purely a new host-plane RPC + `HostFrame`, structurally identical to `workspace.list`/`host/workspace-changed` — not a `SessionEventMap` member, not durable session-log data, not model-visible. `docs/testing.md`'s "both SDKs project the loop" rule does not apply; noted here explicitly so a future reviewer does not ask for a TypeScript/Python SDK update that has no target.

**No change to crew tool-call rendering.** The 8 crew tools (`crew_hire`, `crew_open_ticket`, etc.) keep rendering as generic JSON cards in the transcript (`packages/core/tools/src/presentation.ts`) — this is a separate monitoring panel, not inline tool-call presentation, and was an explicit non-goal kept to bound the change.

## Client-runtime and UI mirroring

`CrewBoardManager`/`CrewBoardRuntime` (`packages/client/runtime/src/client/crew/`) mirror `workspaces/manager.ts`'s `WorkspaceManager`/`WorkspaceRuntime`, scoped to a sparse per-workspace map (`CrewBoardsState.byWorkspaceId`) instead of one process-wide list, since crew has no analog to workspace order or the registry-global archive set. The in-flight-dedup/frame-vs-refresh race handling is the same shape as `WorkspaceManager.refresh()`'s own `refreshFrames` replay, adapted per-workspace: a `host/crew-board-changed` frame landing while that workspace's `crew.board` pull is in flight is guaranteed to reflect a commit at least as recent as the request (the Host pushes synchronously at commit time on every open stream), so it outranks that pull's own response rather than the reverse.

`packages/client/ui-workspace`'s `WorkspaceBrowser.tsx` already owned the sidebar region's whole body (grouped-tree/flat-list/search, switched on `groupBy`/search-query state persisted via `createWorkspaceViewStore`). A fourth persisted field, `viewMode: 'sessions' | 'crew'`, adds a Sessions/Crew tab switch that replaces the section header's previously groupBy-driven static title; selecting Crew swaps the region body to the new board, scoped to the workspace containing the currently selected session (the same resolution the grouped tree's own `currentGroup` already computes) and hides the session-only search/group-by controls. The persist key bumped `v5` → `v6`: rehydration replaces state wholesale (no deep merge with `init()`), so an old blob would otherwise resolve the new `viewMode` field to `undefined` instead of its default. `useCrewBoard` is synthesized from `ctx.crewBoard.list` through the existing hooks-compartment mechanism (`bindSnapshotSelector`, the same pattern `useDirectoryFlow` already uses for the directory-picker occupancy source) — not a new global framework hook, since the Crew panel is its one consumer.

## Deviations from the reviewed plan

The plan's file list did not anticipate that adding `crew` to the `ApiProxy`/`IApiClient`/`RpcMethodMap` interfaces requires updating every existing hand-built implementer of those interfaces, not only the new files: `packages/host/apiproxy/src/fetch/client.ts` (`IApiClient`, `UNARY_VALUE_SCHEMAS`, `AbstractApiClient`), `src/fetch/handler.ts` (`UNARY_ROUTES`), `src/index.ts` (`ApiProxyService`), two hand-scripted `ApiProxy` test doubles in `packages/host/apiproxy/tests/`, `packages/client/connection`'s `api.ts`/`index.ts` re-export barrels and its `FixtureApiClient` (new `FixtureOptions.crewBoard` static seed, since the panel is read-only so no mutation round trip needed simulating), `packages/api/remotes`'s client re-export barrel, and two more `FakeApiClient`/`IApiClient` test doubles in `packages/client/runtime/tests/` and `packages/client/connection/tests/`. All of these compile-fail loud the moment `crew` joins the shared interface, which is the intended fail-loud behavior for adding a domain to a closed interface — the plan simply undercounted how many implementers exist across the wire-type propagation chain (`dsh-host-apiproxy` → `dsh-client-connection` → `dsh-api-remotes` → `dsh-client-runtime`).

`packages/client/runtime/tests/crew-board-manager.client.spec.ts` needed the `.client.spec.ts` suffix (not plain `.spec.ts`) every other test in that directory already uses: `tsconfig.host.json`'s root `include`/`exclude` glob pair is what keeps client-plane tests out of the Host aggregate program, keyed on that exact suffix (`packages/client/AGENTS.md`'s "a test file names the face it covers" rule) — an easy miss since the package-local `tsconfig.json` (`src` only) never catches it; only the root aggregate's `tsc -b tsconfig.host.json` does, and project-reference incremental caching can mask the omission until a forced rebuild.

`packages/test-support/client-runtime` needed a new `TestCrewBoard` double (mirroring `TestWorkspaces`) registered on `SlotTestRuntime`, since `ui-workspace`'s `apply()` now declares `crewBoard` in its cordis `inject` list — every composition test driving that `apply()` needs `ctx.crewBoard` provided or the fiber never runs. This is the same category of ripple as the interface-implementer updates above: a new required service in an existing plugin's `inject` list is a breaking change for every test harness that boots it, by cordis design.

The keyless browser snapshot required by `docs/testing.md` for a new browser-rendered product surface (`apps/web/tests/crew-board.e2e.ts` + `apps/web/tests/snapshots/crew-board/board.expected.md`) needed no `DEEPSEEK_API_KEY` at all, contrary to the reviewed plan's assumption: since roster/ticket seeding goes through `ctx.crew` directly and the Director's pending question comes from calling `ctx.userQuestions.ask()` directly against its live Agent rather than a real tool round trip, the scenario issues zero model calls — the same "Zero model calls" category `workspace-management.e2e.ts` already established, not the `dsh-llm-replay`-fixture category `question-composer.e2e.ts`/`crew-director-preset.snapshot.ts` need. `DSH_SNAPSHOT=refresh` produced the committed golden directly in this environment, and it reproduced deterministically under the default replay mode on rerun (confirmed the recorded escalation banner actually resolves its "Go to session" CTA, i.e. the correlation heuristic matched the seeded Director session for real, not merely in the unit-level derivation tests).

## Alternatives considered

**A mutation RPC (`crew.assign`, `crew.block`, etc.) alongside `crew.board`, so the panel could act on tickets directly.** Rejected: crew's authority model (role/assignee checks inside `CrewRuntime`) already lives entirely in the tool-mediated path; a parallel RPC mutation path would need to re-implement or bypass those checks, and no product requirement asked for panel-driven mutation in this pass.

**Deriving the escalation match from the ticket's `citesMessageIds` or another existing crew field.** Rejected: no existing field names a question or session id; inventing one would be a backend change the linked crew note's own design deliberately avoided for the "which human decision resolves this" relationship (escalation reuses `ask_user_question` precisely to avoid a bespoke escalation-tracking mechanism), and doing it only for this panel would create exactly the "explicit ticket↔escalation link field" the crew note chose not to build.

**A new global framework hook (`useCrewBoard` beside `useSessions`/`useWorkspaces`) instead of the hooks-compartment mechanism.** Rejected: the Crew panel is the sole consumer of crew-board state; `GlobalStandardProps` is for state every global slot component needs, and `useDirectoryFlow`'s existing hooks-compartment pattern already covers "one surface's own single-consumer observable" without widening the framework-wide props every slot component receives.

## Consequences

Bought: live, host-authoritative visibility into a Director-led crew's roster and ticket board from the existing sidebar, with no new package, no new global hook, and no change to crew's own tool-mediated write path or transcript rendering. Cost: the escalation banner's session match can be wrong (false match or no match when one exists) since it is a heuristic over already-computed client state rather than a backend-linked fact; accepted because building the backend link was explicitly out of scope for the underlying crew feature and remains available as later work if the heuristic proves insufficient in practice. The message-pool feed remains entirely unsurfaced; a future pass can add it as a fourth `viewMode` or a per-ticket detail expansion without touching this change's wire contract.
